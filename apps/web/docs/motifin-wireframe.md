## 실행과 검토

저장소 루트에서 `pnpm dev:web`를 실행하고 [월간 리뷰](http://localhost:5173/__wireframes/motifin/review)를 연다. API·DB 연결은 필요 없다. 기존 Web 개발 환경의 MSW를 사용하며 금융 요청은 만들지 않는다.

화면 크기는 **삼성 갤럭시 S25 FE**를 참고한다. 단말의 실제 CSS viewport는 화면 확대·표시 설정에 따라 다르므로 가로를 고정하지 않고 가용 너비를 사용한다. PC에서는 개발자 도구의 반응형 화면에서 단말과 비슷한 크기로 보거나 브라우저 너비를 좁혀 검토할 수 있다. 브라우저별 호환성 검증은 이번 범위가 아니다.

- 첫 진입: 둘째 달인 2026년 9월 리뷰. 월 선택으로 8월과 비교한다.
- 맨 위 **검토 도구**에서 첫 이용, 자료 누락, 카드 명세 지연, 중복·정정, 미분류·금액 분할, 저장된 PDF 암호, 특이 변화 없음, 로딩, 조회 실패를 선택한다. 시나리오 전환·초기화·새로고침은 메모리 변경을 버린다.
- 하단 탐색은 월간 리뷰 / 소비 분석 / 자금 일정. 자료 가져오기는 홈 CTA, 설정은 제품 상단 버튼이다.
- 화면·월·카테고리·상세 시트는 URL로 표현한다. 자금 흐름 구성은 `flow`로 열고, 유입·유출 항목에서 해당 거래 목록과 원거래를 확인할 수 있다. 브라우저 뒤로 가기로 상세 진입 전 화면을 볼 수 있다.
- 가져오기 단계는 화면을 이동했다가 돌아와도 메모리에서 유지된다. 월을 바꾸면 가져오기 단계를 초기화한다.
- 자료 가져오기는 업로드할 월·주기·개수를 정하는 단계 없이 여러 파일 선택으로 시작한다. 첫 이용의 여러 달 일괄 가져오기와 이후 임의 시점의 추가 업로드를 같은 흐름으로 다룬다. 월별 배치는 앱 내부에서 수행하고 가져오기 화면에는 분류표·월별 배정 선택을 보여주지 않는다. 월 선택은 분석 화면에 남긴다.
- 은행·카드 샘플 파일은 8~9월 이용 자료를 표현하는 4개이며 여러 개를 선택할 수 있다. '문제 있는 파일도 시연하기'에는 읽기 실패·다른 계좌 PDF를 추가할 수 있다. 실제 파일 파싱·무제한 업로드를 구현한 것은 아니다.
- 은행 PDF가 선택되면 같은 파일 선택 화면에 PDF 암호 시연을 표시한다. 실제 생년월일 입력 대신 '샘플 암호 입력' 버튼을 사용한다. 저장 여부는 boolean만 메모리에서 유지한다. 저장 시연 후 다음 가져오기는 입력을 건너뛰며 설정의 PDF 암호 관리에서 변경·삭제 상태를 시연한다.
- 별도의 분석 대상 확인 섹션·등록 버튼 없이 자료 선택부터 시작한다. 은행 선택 항목에 대상 통장·결제계좌·입출금·잔액을, 카드 선택 항목에 KB Pay 이용대금명세서·이용·청구·할부를 안내한다. 고객 화면에서는 '원천' 대신 '은행·카드 자료', '관리하는 계좌·카드', '자료 구분'을 사용한다. 개발 인터페이스 이름은 그대로 유지한다.

## 합성 자료의 의미

모든 이름·날짜·금액은 가상이다. 기준은 달력 월이며 시연의 마지막 확인 시점은 10월 2일이다. 자금 일정의 9월은 실제 기록을, 10월 이후는 9월 말 잔액에 기반한 계획을 보여준다.

| 항목 | 2026년 8월 | 2026년 9월 기본 시나리오 |
| --- | --- | --- |
| 이용일 기준 소비·비용 | 1,920,000원 | 1,435,000원 |
| 외부 소득 | 3,200,000원 | 3,200,000원 |
| 통장 기초 잔액 | 1,000,000원 | 2,500,000원 |
| 실제 유입 / 유출 | 3,400,000 / 1,900,000원 | 3,300,000 / 2,055,000원 |
| 통장 기말 잔액 | 2,500,000원 | 3,745,000원 |
| 카드대금 실제 출금 | 600,000원 (7월 이용 자료 없음) | 640,000원 (8월 이용분) |

- 8월 가전 구매 600,000원은 구매월 소비에 한 번 포함한다. 9월 할부 1/5회 120,000원과 10월 2/5회 120,000원은 청구·현금 이동이다.
- 9월 식료품 구매 350,000원에서 연결된 취소 50,000원을 반영한다. 단일 분류의 원거래는 연결 환불에도 같은 분류를 사용한다. 분할 구매의 전체 취소는 원래 배분을 되돌리고, 부분 환불의 용도를 알 수 없으면 미분류로 두어 사용자가 확인한다. 이미 사용자가 확인한 부분 환불 분류는 유지한다.
- 9월 카드 이용 순액 620,000원과 다음 할부 120,000원을 더한 10월 청구 샘플은 740,000원이다. 구독료를 별도 예정 합계에 다시 넣지 않는다.
- 9월 할부 수수료 5,000원은 확인된 비용으로 별도 반영한 시연 가정이다. 실제 비용 인식 시점을 확정하는 결정이 아니다.
- 투자·파킹 통장으로 보낸 금액은 소비가 아니며 수취도 소득이 아니다. 상대 계좌 잔액은 생성하지 않는다.
- 부분 자료에서는 소비 총액·비중·비교를 보류하고 관측된 거래만 보여준다. 예정 금액 미확인은 합계에서 제외하고 개수를 알린다.
- 이 시안의 기간 완전성·중복 판정은 합성 ID와 사전 구성 자료에만 적용된다. 실제 XLS/PDF의 완전성·중복 식별·파싱 가능성을 증명하지 않는다.
- 파일명·청구월과 소비월을 동일시하지 않는다. 카드 9월 청구 샘플은 8월 이용, 10월 청구 샘플은 9월 이용으로 사전 구성했다. 이 매핑·월별 자료 범위는 시연 어댑터 내부 입력이며 고객의 수동 분류 작업이 아니다. 부분 자료는 분석 시점에 표시한다.
- 거래 직접 보정 시연은 카드 소비·환불의 거래명·금액·같은 달 내 날짜·메모를 지원한다. 가져온 값을 보존하고 소비 집계에 보정값을 반영한다. 실제 은행 현금 보정·월 이동·대사 재계산·입력 규칙의 범위는 후속 설계 사항이다.
- 같은 원본의 재업로드는 기존 사용자 보정·분류를 유지한다. 파일 값 자체가 기존 기준과 달라질 때만 충돌로 보여준다. 실제 중복 식별자·문서 개정 판정은 PIN-39 검증 대상이다.
- 월간 리뷰의 증감과 흐름 구성은 합성 원천 어댑터가 제공한다. 원인 후보는 사전에 정한 가전 구매·식료품 비교 시나리오이며 최신 금액과 분류로 문구를 다시 구성한다. 자료가 부족하면 비교·원인 표시를 보류한다. 자동 탐지·AI·예측 엔진을 구현한 것은 아니다. 기존 `insight` 필드는 최초 시안의 값이며 월간 리뷰는 새 `MonthlyReview` 입력을 사용한다.
- 소비 분석의 탐색을 위해 같은 가맹점의 여러 이용, 쿠팡 합성 결제, PG사 합성 결제를 추가하고 기존 합성 금액 일부를 재배치했다. 위 표의 월간 총액·은행 잔액은 유지했다. 쿠팡·PG는 품목을 알 수 없어 미분류로 시작하며 가맹점명으로 용도를 확정하지 않는다.

## 소비 분석과 카테고리 배분

소비 분석은 관점 선택 → 카테고리 상세 → 가맹점/원거래 → 분류 보정으로 이어진다. `focus`와 `sort`는 분석 관점·정렬, `category`는 상세 대상을 나타낸다. 카테고리를 누르면 페이지 내용이 해당 분석으로 전환되고 상단으로 이동한다. 월 이동에서도 카테고리 맥락을 유지한다.

- **규모:** 금액·비중·구매 건수, 가맹점 상위 5곳과 각 거래를 확인한다.
- **변화:** 전월 증가/감소액으로 정렬하고 확보된 달의 순액 추이를 본다. 이전 달이나 해당 월 자료가 불완전하면 비교·전체 비중은 보류한다.
- **반복:** 원거래에 표시된 반복 여부에 따라 구성과 큰 일회성 구매·반복 거래를 본다. 미래 출금과 합산하지 않는다.
- **분류 확인:** 미분류 순액·거래 건수, 나눠 분류한 거래와 원거래를 확인한다. 소비임이 확인된 거래는 카테고리 미확정이어도 총액에 포함한다. 미분류는 지우거나 이름을 바꿀 수 없는 기본 분류다.
- **상세:** 선택 카테고리 순액·전체 비중·전월 차이·현재/전월 구매 건수와 취소 전 건당 평균·환불액, 월별 추이, 반복 구성, 가맹점과 거래를 제공한다. 건당 평균은 구매/비용 발생 금액을 기준으로 하며 취소·환불을 별도 표시한다.
- **배분:** 금액은 원 단위 정수로 입력하고 합계가 원거래 금액과 정확히 같아야 한다. 모르는 부분은 미분류로 배분할 수 있다. 같은 카테고리의 여러 행은 합친다. 총 소비·은행 현금·원거래 수는 분할로 늘지 않는다. 카테고리별 건수는 해당 배분을 포함한 원거래 수이므로 여러 카테고리의 건수를 단순 합산하지 않는다.
- **환불:** 전체 취소는 원래 배분을 반대로 반영하고 부분 환불은 품목/용도 근거 없이 비례 배분하지 않는다. 미분류 환불도 소비 순액에 반영되며 원거래와 연결한다.
- **관리:** 추가·전체 기간 이름 변경·연결 거래 확인·다른 분류로 병합·카테고리 삭제·미분류 이동을 지원한다. 병합은 영향 거래 수와 이동 대상을 먼저 표시한다. 현재 시연은 이름 기반 레지스트리를 일관되게 이동시키며 실제 서비스의 안정적 category ID/보존·이력 정책을 확정한 것은 아니다.
- **재가져오기:** 분류·배분·사용자 보정은 같은 원본 재업로드로 덮어쓰지 않는다. 새 파일/원본 복원으로 거래 총액이 바뀌어 기존 분할이 맞지 않으면 미분류로 돌리고 재확인을 안내한다. 분할된 거래의 직접 금액 수정은 먼저 한 분류로 합친 뒤 시연한다.

화면은 `source.spending(monthId, category)`가 제공하는 read model과 콜백을 받는다. 집계는 개발용 `spending-presentation.ts`에 한정한다. PG사 추론·상품 내역 조회·AI·가맹점 자동 분류 규칙은 구현하지 않으며 이번 수정/분할을 이후 같은 가맹점의 모든 거래에 자동 적용하지 않는다. 실제 카테고리 체계·규칙 관리의 상세 범위는 PIN-37의 후속 결정 사항이다.

## UX 결정과 남은 검토

- **결론과 흐름 우선(사용자 리뷰 반영):** 월간 리뷰를 `이번 달의 결론 → 한 달의 자금 흐름 → 왜 달라졌나요 → 다음 확인`으로 바꿨다. 브랜드·월·설정을 한 줄로 압축하고 정상 자료 상태는 작은 줄로, 누락 상태는 자세히 표시한다. 첫 영역은 소비 변화·통장 현금 변화를 같은 위계로 보여주고 소비 총액·월말 잔액은 기준일 의미를 붙여 보조 표시한다.
- **연결된 현금 흐름:** 기초 잔액 + 유입 − 유출 = 기말 잔액을 연속된 축으로 표현한다. 유입은 급여·내 계좌 수취로, 유출은 직접 소비·비용 / 카드대금 / 다른 내 계좌 이동으로 나눈다. 유출 비중은 막대로 비교하고 각 구성에서 관련 거래를 연다. 이 흐름을 이용일 기준 소비와 합산하지 않는다.
- **원인은 2개까지:** 전월 가전 구매가 소비 감소에 미친 영향과 식료품 변화의 근거를 먼저 설명한다. 전월 원거래·현재 카테고리 거래로 이동할 수 있다. 전체 카테고리 목록은 소비 분석에 두고, 가까운 예정 지출·미확인 항목·자료 갱신은 뒤에서 확인한다.
- **정보 영역 5개 / 주요 탐색 3개:** 월간 리뷰의 큰 흐름에서 카테고리·거래로 내려가고, 가져오기·설정은 지원 경로로 둔다. 관리 부담 감소와 근거 탐색에 기여한다.
- **임의 시점 다중 업로드:** 월간 리뷰 빈도와 업로드 빈도는 다르다. 사용자가 원하는 파일을 원하는 때에 가져오고, 앱이 자동으로 기간·유형을 해석해 내부 저장 대상으로 분류한다. 정상 처리에는 확인 화면을 추가하지 않고 오류·충돌만 질문한다. 고객 용어는 은행·카드 자료와 계좌·카드를 사용한다.
- **암호 재사용:** 사용자 확인에 따르면 은행 PDF 암호는 생년월일 6자리다. 한 번의 가져오기에서 같은 암호를 선택한 은행 PDF들에 적용한다. 선택 저장은 서버 암호화 보관 후 요청 시 복호화해 브라우저에 일시 전달하는 설계 방향으로 PIN-39/40에서 검증한다. 이 시안에는 암호값·DB·암호화·키·네트워크가 없고 저장 상태만 있다. '이 기기에서 기억' 대신 계정 기준 'PDF 암호 저장'을 사용한다.
- **중립적 표현:** 이상 경고 대신 이번 달 발견·확인할 항목을 사용한다. 두 달 비교에서 평소 패턴을 단정하거나 구매 필요를 만들지 않는다.
- **제품 테마의 범위:** 기존 Button/Card/상태 UI를 재사용하고 MOTIFIN 영역에서만 semantic CSS 변수를 덮어쓴다. Mint는 강조, 어두운 녹색은 밝은 표면의 액션에 사용한다.
- **자산 권리:** MOTIFIN 이름·확정 색상만 참고했다. 과거 COP 로고 SVG·폰트 파일·코드는 복제하지 않았고 기존 시스템 글꼴을 사용한다. 직접 재사용 권한은 미확인 상태다.
- **기술 미결:** 실제 암호 PDF/XLS 처리·모바일 파일 접근·자료 기간 판정은 PIN-39, 실제 소유권·저장·API는 후속 설계 범위다.

초기 월간 리뷰 사용자 피드백은 “첫 화면에서 한 달의 분석 결과와 자금 흐름이 보이지 않고 정보가 나열된다”였다. 이에 따라 위 위계로 수정했다. 추가 피드백으로 불필요한 분석 대상 확인을 제거하고, 임의 시점 다중 파일·예외 중심 가져오기와 암호 재사용을 반영했다. 수정 화면의 사용자 재검토와 PIN-52 완료 판정은 아직 수행하지 않았다.

## PDF 암호 보관의 후속 검증

PIN-39의 브라우저 PDF 처리 PoC 뒤 PIN-40에서 실제 저장·소유권·반환 경계를 설계한다. 과거의 서버·DB 비보관 후보는 사용자의 선택 저장 요구에 한해 재검토한다. 이름이 생년월일이더라도 회원 프로필로 별도 수집하지 않고 PDF 잠금 해제 목적의 비밀정보로 다룬다.

- AES-GCM 같은 인증된 암호화, DB와 분리한 서버 key/secret 관리, 사용자·용도 결합, key version·교체를 검토한다. 생년월일 자체를 암호화 키로 쓰지 않으며 복원이 필요하므로 해시만 저장하지 않는다.
- 업로드 실행 때만 로그인·객체 소유권 검사 후 HTTPS로 일시 반환한다. 응답은 no-store, 클라이언트는 처리 중 메모리로 제한하며 종료 시 참조 정리. 비밀번호·키·원본·민감 본문의 로그/URL/Analytics 노출을 방지한다.
- 저장은 선택이며 변경·삭제를 제공한다. 서버 침해·세션 탈취·XSS까지 저장 암호화로 막는다고 주장하지 않는다. 서버 PDF 처리 방식과 비교할 때 금융 원본의 서버 전송 부담도 평가한다.
- 이 문서는 설계 방향 기록이다. 실제 암호 저장·복호화·DB migration·계약·인가·보안 검증은 이번 시안 구현에 포함하지 않는다.

## 수행 범위

2026-10-25 요구 반영 후 `pnpm --filter @innova/web typecheck`와 diff 공백 검사는 통과했다. 사용자 요청에 따라 테스트·build·브라우저 QA·로컬 서버 실행은 생략했으며 이번 변경의 lint는 실행하지 않았다. 실제 PDF/XLS 처리·서버/DB 암호 저장·인가·보안·production 번들 검증은 수행하지 않았다. 실제 기능의 완료 결과로 해석하지 않는다.

## 자금 일정과 소비재 계획 — 2026-10-25

기존 예정 지출을 **자금 일정**으로 변경했다. 조회월에 속한 입출금만 본문에 표시한다. 9월은 실제 거래·월말 잔액과 10월 계획 진입 버튼, 10월은 통장 현금 예상을 제공한다. 날짜·금액은 모두 기존 시안과 연결한 합성 자료이며 실제 사용자 일정이 아니다.

- `calendar(monthId)` read model과 `saveCalendarEvent` / `changeCalendarEvent` / `setProtectedAmount` 액션을 주입한다. 계산·반복 일정 전개·변경은 개발용 `calendar-presentation.ts`에 한정하며 UI는 데이터·콜백을 받는다. 실제 원장·파일·서버·알림은 변경하지 않는다.
- 마지막 확인 잔액 + 남은 예정 수입 − 남은 예정 출금 = 월말 예상 잔액. 이후 납부할 카드 금액과 선택한 보존 금액을 더 빼면 **남은 생활비 예상**이다. 앞으로 쓸 일상 생활비를 포함한 몫으로, 오늘 즉시 사용 가능한 잔액이나 투자 여력을 뜻하지 않는다.
- 10월 시작 잔액 3,745,000원, 예상 급여 3,200,000원, 월세 700,000원, 카드 청구 740,000원, 계획 이체 600,000원. 공과금은 미확인으로 두어 이후 잔액·생활비 예상을 보류한다. 공과금을 110,000원으로 입력하면 월말 예상 4,795,000원. 이후 카드 납부를 위한 425,000원(잔여 할부 360,000원 + 등록한 10월 카드 계획 65,000원)과 합성 보존 설정 500,000원을 빼면 생활비 예상은 3,870,000원이다. 미등록 소비는 포함하지 않는다.
- 확인한 구간의 최저 잔액·날짜와 다음 수입 전 출금을 보여준다. 검토 도구 **급여 전 잔액 부족**은 10월 14일 가상 목돈 4,000,000원을 추가한다. 공과금 미확인 이전의 부족을 확인할 수 있다. 같은 날의 입출금 처리 순서는 추정하지 않고 날짜 말 잔액만 표시한다.
- 은행·카드 누락, 미확인 금액, 앞선 달의 미확인 계획은 0원으로 취급하지 않는다. 이후 달은 새 카드 이용·다음 청구 미확인을 알리고 생활비 예상을 보류한다. 월말 자료를 실시간 현재 잔액으로 표시하지 않는다.
- 카드대금은 통장 출금, 카드 구독·정기배송은 이후 납부를 위해 보존할 금액으로 분리한다. 카드대금에 포함된 구독·할부를 다시 출금으로 더하지 않는다. 확인된 청구 금액은 계획 편집으로 덮어쓰지 않고 소비 보정에서 갱신한다. 포인트는 현금 합계 제외, 투자·파킹 이체는 소비와 구분한다.
- 일정 추가, 금액 미확인/예상액/확인액, 이번 회차 수정/이후 반복 수정, 회차 건너뛰기/복원, 이번 회차부터 반복 종료를 메모리에서 시연한다. 반복일이 해당 월 마지막 날을 넘으면 말일로 제한한다. 휴일 이동·실제 거래 자동 매칭·예정과 실제 차이 대사는 구현하지 않았다. 과거 거래는 실제 기록 링크로만 제공한다.
- **세제·영양제·화장품의 재구매 시점 예측과 재고 관리는 제외**한다. 직접 정한 일회 구매 계획과 신청한 정기배송만 등록하며 구매 간격에서 일정을 만들지 않는다. 첫 이용에는 사전 일정이 없다.

카테고리 삭제 버튼은 관리 목록에 항상 노출한다. 미분류 기본 항목은 삭제할 수 없다. 거래가 연결되어 있어도 삭제할 수 있으며 모든 기간의 해당 배분만 미분류로 이동한다. 원거래·총액·다른 카테고리 배분을 보존하며 동일 거래 안 미분류 배분은 합친다. 재가져오기 별칭도 미분류로 연결하여 삭제한 기본 분류가 되살아나지 않게 한다. 다른 분류로 옮기는 병합은 별도 편집 기능으로 유지한다.

검토: 자금 일정 9월 → 10월 계획 → 공과금 금액 입력 → 예상액 확인 → 영양제 일정 건너뛰기/복원 → 계획 추가/반복 변경 → 부족 시나리오. 카테고리 관리에서는 거래가 있는 주거를 삭제하고 미분류·원거래 총액을 확인한다. 모든 변경은 새로고침 시 초기화한다.
