# MOTIFIN 은행·카드 비즈니스 반영

상태: PIN-57/58 로컬 구현·dev 검증 대상. 운영 적용·월간 분석·투자 자산 관리를 뜻하지 않는다. 입력·기본 가져오기는 [Raw 적재](finance-raw-ingestion.md), 제품 경계는 [MOTIFIN](../../web/docs/motifin-product.md), 테이블 메타는 [신규 테이블 기준](../../../docs/database-table-metadata.md)을 따른다.

## 원천에서 해석 결과로

기존 `/motifin/import`에서 파일을 가져오면 Raw 저장/readback 뒤 비즈니스 해석을 요청한다. 이미 저장한 파일은 파일 재업로드 없이 ‘거래 반영 확인’으로 처리 결과를 다시 조회한다. Raw 저장 성공과 해석 성공/보류/실패를 구분하며 해석 오류가 원천 저장을 취소하지 않는다. 화면에서 은행·카드 자료 → 기록 상세 → 페이지/행·추적 순서와 관련 보조행을 확인한다. 월간 리뷰/카테고리 분석은 PIN-59 이후 범위다.

지원된 KB 원화 양식을 KRW scale 0의 정수 문자열/BigInt로 처리한다. 해당 양식의 제품 해석이며 범용 외화·환율 처리를 제공하지 않는다. 빈 값과 0을 구별하고 금액·날짜 오류/overflow는 불명확한 성공 대신 invalid로 보류한다. 원파일과 Raw는 금융기관 진위 증명이 아니며 원문/사용자 데이터는 Git/Linear/fixture에 넣지 않는다.

| 테이블 | 메타·키·역할 |
| --- | --- |
| finance_business_scopes | owner PK + revision. 문서 간 반영 판단의 내부 CAS 조정자다. 업무 객체가 아니므로 created/updated_at을 일률 추가하지 않는다. |
| finance_business_documents | 서버 ID, owner·Raw 파일 복합 FK, processor version별 유일성, created_at·원천 범위·결과 상태. owner가 요청 주체이고 processor version이 자동 처리 출처다. 결과는 불변이며 수동 updated_by/revision을 중복 추가하지 않는다. |
| finance_business_events | ID, owner·문서·Raw 파일 및 실제 Raw 행 복합 FK. 원천 sequence + source page/row·관련 보조행을 보존한다. 금액·텍스트 payload는 인증 암호화하고 생애주기는 문서를 따른다. |

단일 SQL statement의 owner revision CAS → 문서 → 전체 이벤트를 한 번에 commit한다. CAS를 잃으면 최신 반영 결과를 읽고 다시 판단한다. 서로 다른 겹친 파일이 병렬 도착해도 둘 다 자동 확정되지 않는다. 같은 Raw/processor 재시도·응답 유실은 같은 결과 ID로 readback하며 Raw를 덮거나 복제하지 않는다. processor 변경·보정은 기존 결과를 직접 갱신하는 별도 경로를 만들지 않고 후속 버전/선택 정책으로 설계한다.

문서/이벤트 payload는 기존 독립 Raw 키의 별도 `finance-business` AAD(owner/id/용도)로 AES-GCM 암호화한다. 계좌 비교값은 HKDF로 목적 분리한 HMAC 키와 owner를 결합해 저장하며 평문 계좌/금액을 인덱스·로그에 두지 않는다. 키 관리/rotation의 운영 제약은 Raw 안내와 같다.

## 은행 현금 기록

은행의 계좌번호·조회기간·총 입금/출금, 각 행의 현지 거래 일시·입출금·잔액을 해석한다. 원천에 timezone이 없으므로 UTC 시각으로 임의 변환하지 않는다. 동일 시각의 별도 원천 행을 합치지 않고 순서/잔액 연결을 검산한다. 거래 순서를 검산한 뒤 기초 잔액은 첫 거래에서 역산한 값, 기말은 마지막 거래 후 값임을 구별한다.

입금/출금의 음수 또는 한 행의 동시 양수는 의미가 불명확하므로 invalid로 보류한다. 기간 안의 입출금 합계와 문서 제어 합계, 인접 거래 후 잔액, 정렬·기간 경계를 검사한다. 불명확/불일치는 전체 파일 invalid이며 확정 이벤트를 만들지 않는다. 직접 이어지는 파일의 기초/기말 잔액도 비교한다. 표시 기간이 달력 월 전체인지는 문서 범위의 속성일 뿐 전체 금융 자료 완전성이나 현재 실시간 잔액을 뜻하지 않는다.

급여/이체/카드대금 텍스트는 **분류 후보**다. 현금 입출금 사실과 그 성격을 구분한다. 은행 outflow의 consumptionAmount는 null이며, 카드대금·타계좌 송금을 자동 소비로 합산하지 않는다. 상대 계좌의 잔액·보유/투자 목적도 만들지 않는다. 첫 관리 계좌와 다른 은행 계좌는 새 반영을 보류한다.

## 카드 이용·청구·조정

구매 관측(G), 회차 청구원금(I), 수수료(J), 잔여 원금(K), 할부 회차(H)를 분리한다. B의 두 자리 연도는 해당 지원 양식에서 20YY로 해석하며 다른 세기/양식 지원을 약속하지 않는다. 구매일을 청구일/출금일로 복제하지 않는다. 청구월·결제일은 Raw에 명시된 필드가 있을 때만 사용하고 파일명에서 만들지 않는다. 현재 제공된 실파일에는 근거가 없으므로 unknown으로 유지한다.

첫 회차/일시불은 관측 구매액으로 표시하지만 이후 할부 회차의 원구매는 확인 필요이며 consumptionAmount=null이다. 주행의 음수 값·취소/환불 표기와 원거래 연결이 불명확하면 확인 대상으로 남긴다. 보조행 G/J의 음수는 부모 원천과 연결된 조정 관측이다. 이를 새 구매·확정 환불 또는 임의 날짜의 소비로 만들지 않는다. 관련 구매의 소비 합계를 보류한다. 빈 수수료는 0으로 대체하지 않고 청구 총액도 미확인으로 남긴다.

명세의 구매 관측 기간은 전체 이용월의 완전성을 증명하지 않는다. 카드 coverage는 unknown, fullCalendarMonth=false다. 확보되지 않은 취소/미청구·청구기간을 채우지 않는다. 수수료·포인트와 소비 인식 시점의 상세 정책은 원천 근거를 늘린 뒤 정하며 포인트는 현금 이벤트로 만들지 않는다.

## 여러 파일과 충돌

- 같은 바이트 문서 idempotency는 PIN-56이 소유한다. 같은 Raw의 재처리는 같은 비즈니스 결과를 반환한다.
- 서로 다른 은행 파일의 중첩 기간/재발급·정정, 카드 명세의 겹친 구매 관측 기간/같은 결제일·반복 구매 의심은 새 문서를 needs-review로 보류한다. 날짜+금액/표시값 동일만으로 확정 병합하지 않는다.
- 카드 표시·가맹점/부가표시·구매액이 같은 교차 문서 관측은 날짜가 달라져도 정정 후보로 보류한다. 비교값은 purpose/owner를 분리한 HMAC이며 동일 거래의 증명이 아니다. 실제 정기 결제도 확인 대상이 될 수 있고, 모든 표시값이 바뀐 정정을 식별한다고 약속하지 않는다.
- 보류 문서는 제안 이벤트 수·이유·기존 후보 문서 ID와 Raw 연결을 보존하되 확정 이벤트 0개다. 일부 신규 거래가 섞여 있어도 전체 파일을 보류하여 중복 합산을 막는다. 기존 확정본을 덮지 않으며 새 보류 문서와의 충돌 경고를 화면에서 연결한다.
- 카드에 안정 ID가 없고 인쇄 카드 표시명이 변할 수 있어, owner의 KB Pay 명세 범위에서 보수적으로 기간 중첩을 확인한다. 서로 다른 카드가 포함된 명세도 자동으로 분리·병합하지 않는다.

행별 승격·정정본으로 기존 거래 교체·수동 중복 판정 확정 UI는 미구현이다. 이번 완료 기준은 무근거 자동 병합 대신 추적 가능한 보류로 충족하며, 지속 운영 전 보류 해소 정책·제품 흐름은 후속 결정이 필요하다. 보류 자료를 다시 처리한다고 근거 없이 자동 해소하지 않는다.

## 청구와 은행 출금 연결

확정 은행 기록의 카드대금 후보, **원천에 있는** 카드 청구월·결제일, 알려진 청구원금+수수료 합계가 있어야 비교한다. 같은 날짜·금액의 양방향 유일한 후보만 matched로 표시한다. 다중 후보/다중 명세의 같은 출금, 금액 불일치, 원천 날짜/총액 없음은 각각 ambiguous/amount-mismatch/missing-period/unknown-total/unmatched로 구별한다. 날짜·수수료를 몰래 보정하거나 카드 소비와 은행 출금을 다시 합산하지 않는다.

현재 실파일은 은행/카드 관측 기간도 맞지 않아 실제 매칭 성공을 검증한 자료가 아니다. 맞는 날짜·금액/불일치/다중 후보는 합성 자료로 검증하며 실자료는 미연결 상태가 올바른 결과다. 이 연결은 현재 자료에서 계산한 read model이며 확정된 결제 사실을 영구 수정하는 기능이 아니다.

## API·Web·검증 경계

`/api/finance/business`: `POST /process {rawFileId}`, `GET /documents`, `GET /documents/:id`. shared contract에서 응답과 금액/상태/원천 연결을 검증한다. 인증·현재 approved·owner·expected actor·Origin/JSON·no-store·안전한 오류 경계를 Raw와 동일하게 적용하며 관리자도 타인의 자료를 볼 수 없다.

Router loader/action이 조회·재검증을 조정한다. entities/finance-business는 query/API, features/finance-business는 처리·독립 readback·성공 cache 반영·세션 취소를 소유한다. 모든 금융 key는 owner/epoch와 보호 cache 제거에 등록되며 원본 암호/파일을 저장하지 않는다. 비활성 query의 GC는 60초로 두어 loader 완료와 lazy 화면 구독 사이에 내역이 사라지는 것을 막고, staleTime 0으로 진입마다 재검증한다. 세션 전환·인가 오류에는 이 시간과 무관하게 즉시 보호 cache를 제거한다. 해석 성공을 확정 cache에 먼저 반영하고 후속 조회 실패로 이미 끝난 작업을 되살리지 않는다.

현재 owner당 해석 문서 10,000개/결제 후보 조회 시 은행 기록 50,000개를 넘으면 안전한 오류로 중단한다. 제한 때문에 오래된 충돌 후보를 조용히 누락한 채 새 파일을 확정하지 않는다. 지속 사용의 pagination/보존·성능 정책은 별도 확인한다.

구현·단위/실 PostgreSQL·실 Neon dev·브라우저·실단말·운영 결과는 각각 구별한다. 변경별 migration·기존 데이터 보존·실행 결과는 [PIN-57](https://linear.app/pin-dev/issue/PIN-57), 카드 원구매/회차·unknown 판정과 검증은 [PIN-58](https://linear.app/pin-dev/issue/PIN-58)이 소유한다. 실제 개인 파일·값·암호·원본 hash는 결과 기록에 복제하지 않는다.
