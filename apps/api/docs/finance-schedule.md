# 자금 일정·이번 달 발견

상태: PIN-62 로컬 구현. `/motifin/schedule?month=YYYY-MM`은 사용자가 등록한 반복·일회 계획과 [은행/카드 원천](finance-business-ingestion.md)·[소비 분석](finance-spending-analysis.md)을 구별한다. 등록된 계획만 전개하며 미등록 소비재의 재고/구매 간격·자동 재구매일·휴일 이동·미납·납부 완료를 추정하지 않는다.

## 계획과 회차

이름·월·예정일·금액(모르면 null)·수입/지출/타계좌 이체·은행/카드/포인트·예상/사용자 확인 예정액·반복 여부·메모를 입력한다. 수입/이체는 관리 통장 방식만 허용한다. 등록하지 않은 비용은 0원인 비용으로 만들어 채우지 않는다. 첫 이용에는 사전 일정이 없고 실제 발생 연결을 반복 강제하지 않는다.

반복은 월별 버전 구간으로 저장한다. 조회월부터 이후 변경/중단은 그 전 회차를 유지한다. 사용자가 따로 확정한 회차 override는 이후 규칙 변경으로 덮지 않는다. 31일처럼 해당 월에 없는 날은 말일로 제한하며 이를 표시한다. 이번 회차만 날짜·금액·분류를 바꾸거나 건너뛰기/다시 포함할 수 있다. 날짜는 원래 회차의 앞/뒤 한 달 안에서 직접 이동할 수 있고, 원래 회차 ID를 유지하면서 실제 예정일의 달에서 표시한다. 은행/카드 원천 날짜를 수정하지 않는다.

반복 중단 뒤에도 이미 연결한 실제 회차는 보존한다. 이 회차를 새 예정액으로 되살리지 않는다. 중단 상태에서 연결을 해제하면 원천 거래 자체는 유지되고 일정의 실제 연결만 해제된다. 한 실제 근거는 여러 회차에 중복 연결하지 못한다. 미래 규칙을 특정 시점부터 다시 활성화하면 그 사이 중단 구간은 보존한다.

## 실제·청구·예정의 의미

사용자가 소유한 확정 은행 입금/출금, 유효 카드 구매(연결 환불 반영), 결제일/청구월 근거가 있는 문서 청구를 선택해 연결한다. 앞뒤 한 달의 근거만 허용하며 성격이 맞지 않거나 정정 후보가 있는 원천은 새 연결을 차단한다. 기존 연결의 원천이 이후 재확인 상태가 되면 그 사실을 표시하고 발생 확정을 재검토한다. 조회할 수 없는 연결을 완료 처리하지 않는다.

카드 명세 청구의 근거 ID는 개별 행이 아니라 **전체 문서 ID**이며 문서 청구 합계를 참조한다. 청구 확인은 실제 통장 출금/납부 완료가 아니므로 해당 통장 계획을 여전히 발생 미확인으로 둔다. 실제 통장 출금 연결과 구별한다. 카드 이용 계획은 이후 납부할 기록으로 구별하고 은행 출금 계획 합계에 넣지 않는다. 포인트는 현금 합계에서 제외한다.

원천에서 확인한 카드 청구는 별도 읽기 목록이며 계획 편집으로 덮지 않는다. 청구월/결제일이 없으면 임의 일정으로 만들지 않는다. 은행 출금과의 matched는 PIN-58이 계산한 근거를 사용한다. 계획 합계·명세 합계·소비·실제 잔액을 새로운 단일 총액으로 합산하지 않는다.

발생 확인 전 계획 합계는 등록한 회차 중 건너뛴 것/실제 연결한 것을 제외한 값이다. 금액 결측이 하나라도 있으면 해당 그룹 합계는 null이다. 예정일 경과/미연결은 미납이 아니며 사용자에게 중립적으로 표현한다. 현재 통장 잔액·소비 원장에는 어떤 계획도 선반영하지 않는다. 전체 월 현금 예측·남은 생활비 예측은 원천/미등록 계획 범위가 불충분하여 이번 기능에서 확정하지 않는다.

## 발견과 근거

발견은 실제 연결한 기록과 계획의 금액 차이, 사용자가 등록한 반복 일정 첫 회차의 관측, 비교 조건을 만족한 두 달의 큰 카테고리 관측 차이만 제공한다. 카테고리 변화는 완전한 월 비교나 소비 패턴의 원인으로 단정하지 않는다. 자료 미확인/정정이 있으면 해당 비교를 억제한다. 없음/비교 기간 부족/변화 없음은 정상 결과이며 빈 화면을 채우려고 신호를 만들지 않는다. 문서 또는 두 달의 카테고리·거래로 근거를 연결한다.

## 저장·권한·경합

신규 `finance_schedule_workspaces`는 owner PK/FK, revision, 생성/수정 시각과 암호화 현재 상태를 가진다. 단일 작성·수정 주체가 인증 owner이므로 created_by/updated_by를 중복하지 않는다. `finance_schedule_revisions`는 (owner, revision) PK, owner FK, operation 유일성, 생성 시각과 불변 command/result snapshot이다. 사용자 삭제 시 둘 다 cascade하며 개인 금액·일정·메모는 기존 독립 Raw 키의 별도 `finance-schedule` AAD(owner/revision/state 또는 history)로 AES-GCM 보호한다.

plan/evidence JSON 내부 참조는 원소별 SQL FK가 아니라 owner의 실제 계획/원천을 서버에서 검증한다. 현재 원천의 개별 삭제/교체 API는 없고 사용자 삭제는 연결 데이터까지 cascade한다. 향후 교체 정책은 PIN-57/58과 함께 다뤄야 한다. owner별 workspace CAS + 이력 INSERT는 단일 SQL로 commit한다. expectedRevision 경합은 409, 같은 operationId/내용의 재시도는 이력을 추가하지 않는다. 같은 ID의 다른 내용은 409다. 과거 수정 이력은 저장하지만 별도 이력 복원 UI는 이번 일정 범위가 아니다.

`GET/POST /api/finance/business/schedule?month=YYYY-MM`은 approved·owner·expected actor·Origin/JSON·no-store를 검증한다. 관리자 역할은 타인 일정 접근 권한이 아니다. Web command는 성공 결과를 먼저 cache에 반영하고 독립 readback 실패가 성공을 취소하지 않게 한다. owner/epoch/month query, 세션 전환 취소와 cache 제거를 사용한다. API/MSW는 공유 pure model과 동일한 plan/evidence 조건을 따른다.

owner당 계획 200개/월별 버전 1,200개/개별 회차 5,000개/변경 10,000개와 원천 조회 제한을 넘으면 중단하고 일부만 합산하지 않는다. 운영용 pagination/장기 보존·키 rotation의 상세 운영은 별도 검토가 필요하다. 이 기능의 합성 dev·모바일 검증과 적용/정리 결과는 [PIN-62](https://linear.app/pin-dev/issue/PIN-62)가 소유한다. 사용자 결정에 따라 실파일 추가 전송은 제외한다.
