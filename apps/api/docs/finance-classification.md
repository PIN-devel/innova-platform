# 카드 소비 분류·보정

상태: PIN-59 로컬 구현. [비즈니스 반영](finance-business-ingestion.md) 결과에 사용자의 선택을 별도로 적용한다. 원천 Raw·은행 현금·청구 금액·기존 비즈니스 이벤트는 수정하지 않는다. 운영 적용이나 전체 소비월 완전성 검증을 뜻하지 않는다.

## 사용 흐름

`/motifin/import`의 ‘소비 분류·금액 나누기’에서 `/motifin/spending`으로 진입한다. 관측 소비 요약 → 카테고리 → 가맹점 → 원거래 순서로 탐색한다. URL의 category/event가 선택을 유지한다. 원천 문서의 페이지·행·추적 순서를 연결한다. 개발용 PIN-52 시안과 달리 이 경로는 저장된 비즈니스 거래를 읽는다.

원 단위 정수 문자열과 BigInt로 계산하며 배분 합계가 유효 거래 금액과 정확히 같아야 한다. 같은 분류의 배분은 합친다. 거래명·같은 원천 월 안의 유효 날짜·소비 금액·메모를 보정할 수 있다. 분할 배분행은 원거래 수에 추가하지 않고, 카테고리 건수는 해당 카테고리 배분이 있는 원거래 수다. 카테고리별 건수를 합산하면 중복될 수 있다. 요약은 현재 확보한 전체 자료의 관측 순액이며 월간 리뷰/대시보드(PIN-60)를 대신하지 않는다.

미분류는 삭제/이름 변경할 수 없는 기본 분류다. 카테고리는 owner 안에서 안정된 UUID를 사용한다. 이름 변경은 ID와 모든 거래의 연결을 유지한다. 병합 또는 삭제 전에 전체 기간 영향 원거래 수·이동 대상을 보여주고 해당 배분만 이동한다. 삭제 대상은 미분류다. 이력의 카테고리가 이후 삭제되었다면 복원 시 미분류로 옮기며 삭제한 카테고리를 되살리지 않는다. 이후 같은 가맹점 거래에 자동 규칙을 소급 적용하지 않는다.

## 미확인 원천·환불

이후 할부 회차·금액 결측·발생월을 뒷받침할 원천이 없으면 새 소비로 보정할 수 없다. 불명확한 구매/음수 조정은 기본 합계에서 제외하고 원천 확인·소비 성격 확인을 사용자가 명시해야 한다. 보조행의 연결 원구매일은 편집 가능한 월의 근거이며 환불 발생일의 증명이 아니다. 사용자가 확인한 날짜를 입력한다. 날짜 근거가 없는 수수료도 자동 구매일로 확정하지 않는다.

음수 환불은 소유한 양수 카드 원구매에 명시적으로 연결하며 연결 환불 합계는 보정된 구매액을 넘을 수 없다. 구매 감액·복원도 이 제약을 지켜야 한다. 전체 취소를 미분류로 지정하면 원구매 배분의 반대액으로 계산한다. 부분 환불은 용도를 추정하지 않고 미분류로 두거나 사용자가 분류한다. 원구매·환불은 개별 원천 기록이며 원거래 수와 순액을 구분한다. 청구 원금·수수료 조정·은행 카드대금을 다시 소비로 더하지 않는다.

## 재가져오기·복원·경합

보정은 business event ID에 연결한다. 동일 Raw 재처리/파일 재업로드는 같은 event ID를 반환하므로 보정·분류를 유지한다. 다른 파일의 원천 금액 정정은 PIN-57/58의 보류 문서로 남고 기존 확정본과 연결된다. 연결된 기존 거래는 sourceReview로 재확인을 표시한다. 새 금액에 기존 보정/배분을 자동 이식하지 않고 기존 합계임을 알린다. 정정본 승격·행 교체는 PIN-57/58의 후속 보류 해소 정책이 필요하다.

원본 복원은 사용자 보정을 제거해 원천 의미/미분류로 돌아간다. 수정 이력에서 특정 거래의 이전 사용자 값을 복원하는 새 revision을 만들 수도 있다. 다른 거래·현재 카테고리 관리 결과는 되돌리지 않는다.

모든 변경은 expectedRevision과 operationId를 사용한다. owner별 workspace revision CAS와 이력 INSERT를 한 SQL statement에서 commit한다. 동시 변경은 하나만 성공하고 나머지는 409로 최신 내역 확인을 요청한다. 같은 operationId·내용의 재전송은 추가 이력을 만들지 않으며 내용이 다르면 409다. 이 식별자는 화면의 편집 수명 동안 유지한다. GET 재조회 실패가 이미 확정된 POST를 취소하지 않으며 Web은 성공 응답을 먼저 캐시에 반영한다.

## 저장·소유권

새 `finance_classification_workspaces`는 owner PK/FK, revision, 최초 생성/최종 수정 시각, 암호화 현재 상태를 가진다. 유일한 작성·수정 주체는 인증 owner이므로 중복 created_by/updated_by는 두지 않는다. 새 `finance_classification_revisions`는 (owner, revision) PK·owner FK·operation 유일성·생성 시각과 암호화 command/결과 snapshot을 가진 불변 이력이다. 개인정보 삭제 단위는 owner이며 사용자 삭제 시 모두 cascade한다.

JSON 안 event/category 참조는 owner의 실제 비즈니스 이벤트·카테고리를 읽어 서버에서 검증한다. JSON 원소마다 관계 FK를 갖는 구조는 아니다. 현재 비즈니스 이벤트에는 개별 삭제/수정 경로가 없고 사용자 삭제는 이력까지 cascade한다. 향후 이벤트 교체/삭제가 추가되면 참조·이력 보존 정책도 함께 설계해야 한다. 삭제된 원천을 조회 결과에 임의로 되살리지 않는다.

기존 Raw 전용 키에서 별도의 `finance-classification` AAD(owner/revision/state 또는 history)를 사용한 AES-GCM으로 현재 상태·수정 이력을 보호한다. 개인 설명/금액/카테고리를 인덱스·로그에 넣지 않는다. 키 관리/rotation의 제약은 Raw 지침을 따른다. 원천 파일·PDF 암호는 사용/저장하지 않는다.

`GET/POST /api/finance/business/classification`은 approved·owner·expected actor·Origin/JSON·no-store를 검증한다. 관리자도 타인 거래를 수정할 수 없다. 공유 Zod 계약과 동일한 pure model로 API/MSW를 검증하며 실제 SQL의 CAS/암호화는 별도 PostgreSQL 테스트가 검증한다. 이력은 owner당 10,000회, 카드 이벤트는 10,000개, 카테고리 100개까지 지원하며 초과 시 과거 내역을 조용히 누락하는 대신 중단한다. 지속 운영용 pagination/보존·성능 정책은 별도 범위다.

Router loader/action, entities query/API, features command 분리를 유지한다. owner/epoch query key는 세션 전환·권한 오류 시 즉시 제거하고 늦은 GET/POST가 다음 사용자 캐시를 채우지 못하게 한다. 상세 입력·보정값은 영구 브라우저 저장소에 두지 않는다. 현재 합성 자료만 검증하며 실파일 추가 전송은 사용자 결정으로 제외한다. dev migration·검증·정리 기록은 [PIN-59](https://linear.app/pin-dev/issue/PIN-59)가 소유한다.
