# Linear 운영 정책

상태: 현행 정책. Pin(PIN) 팀 / Innova Platform 프로젝트의 저장소 작업에 적용한다.

## Label·Milestone·Issue의 역할

| 항목 | 역할과 선택 기준 |
| --- | --- |
| Label | 지속적인 업무·제품 영역이나 작업 성격을 분류한다. 달성 목표·우선순위·진행 상태를 대신하지 않는다. |
| Milestone | 프로젝트 안에서 목표 시점·범위·완료 기준이 명확한 결과물 또는 제품/기술 단계를 묶는다. 상시 업무 분야나 개선 후보의 영구 보관함으로 쓰지 않는다. |
| Issue | 목표·범위·AC·검증 방법을 가진 개별 작업 단위다. 채택한 개선의 실행과 완료 판정도 독립 Issue가 소유한다. |
| Improvement Inbox | 아직 채택하지 않은 공통 개선 후보를 모으는 상시 Issue다. 등록은 구현 승인이나 일정 약속이 아니다. |

### Area Label과 작업 성격

`Area`는 주요 영역 **1개**를 선택하는 Label 그룹이다. 그룹 자체를 이슈에 붙이거나 Platform과 Engineering을 동시에 선택하지 않는다.

| Area | 기준 |
| --- | --- |
| Platform | 여러 서비스가 공유하는 제품/앱 기능: 인증·계정·디자인 시스템·공통 컴포넌트 등 |
| Engineering | 품질·테스트·개발 워크플로·DB 변경·백업·복구·배포 운영 신뢰성 등 |
| 서비스별 Area | 해당 서비스가 책임지는 제품 작업. Personal Finance, Exam Drill 등 기존 Label 중 주요 영역을 선택한다. |

공통 컴포넌트와 그 테스트를 함께 구현하더라도 중심 결과물이 공통 UI라면 Platform을 선택한다. CI·회귀 검증 체계 자체를 개선하는 작업은 Engineering이다. 출처 서비스와 영향 영역은 본문·관련 이슈 링크로 보완하며, 이를 표현하려고 Area를 중복 선택하지 않는다. 작업 성격은 기존 Feature / Bug / Improvement Label을 필요에 따라 별도로 사용한다. 후보가 여러 영역에 걸친 Inbox 자체에는 Area를 억지로 지정하지 않고 댓글에 후보별 Area를 적는다.

2026-10-24에 Area 그룹의 단일 선택 설정과 기존 Label을 Connector로 확인했다. 실제 변경 시에는 현재 목록을 확인하며 새 Label·그룹을 임의 생성하지 않는다.

### Milestone 지정과 기존 이력

새 Issue에 적합한 달성 목표가 없으면 Milestone을 비워 둔다. 모든 Issue의 Milestone을 채우기 위해 새 목표를 만들거나 상시 업무 분야를 배정하지 않는다. 구체적인 목표가 합의되었을 때 필요한 작업만 연결한다.

기존 `플랫폼 공통 기반 및 운영 신뢰성`, `신규 도메인 기능 확장`은 과거 포괄 분류 이력을 보존한다. 신규 작업을 이름만 보고 자동 배정하거나 Platform / Engineering 같은 영구 분야별 Milestone으로 분할하지 않는다. 과거 연결·진척을 일괄 재배치하는 작업은 별도 범위다.

## 공통 개선 후보 수집과 처리

상시 수집함은 [PIN-53 — Platform Improvement Inbox](https://linear.app/pin-dev/issue/PIN-53)다. 프로젝트·담당자를 유지하고 Milestone 없이 Backlog로 둔다. 후보 기록·일부 후보 처리 때문에 In Progress나 Done으로 바꾸거나 PR의 closing 대상으로 연결하지 않는다.

### 발견 시 기록

1. 현재 작업의 AC를 막는 버그·보안 위험·장애인지 먼저 구분한다. 그런 문제는 Inbox에만 남겨 미루지 않고 현재 이슈 또는 필요한 독립 이슈에서 처리한다.
2. 당장 처리하지 않아도 되는 공통 개선 후보라면 PIN-53의 관련 댓글을 확인한다. 같은 후보가 있으면 해당 스레드에 출처·새 근거만 보완하고, 새 후보만 댓글 하나로 추가한다. 전체 backlog를 매번 조사하지 않는다.
3. 댓글에는 **출처 이슈/PR / 후보 Area → 관찰한 문제·반복 징후 → 영향·개선 아이디어 → 지금 처리하지 않는 이유**를 짧게 적는다. 관찰 사실과 아직 검증하지 않은 기대 효과를 구분하고 비공개 자료·비밀 값은 넣지 않는다.
4. 서비스 내부 개선은 해당 서비스 이슈가 먼저 소유한다. 여러 서비스에서 공통화할 가능성이 있을 때만 Inbox에 요약과 출처 링크를 남긴다. 후보 원문은 댓글이 소유하며 Inbox 본문·별도 문서에 목록을 중복 관리하지 않는다.

기록 자체로 독립 이슈·우선순위·일정·Milestone·선행 의존을 만들거나 현재 기능의 범위를 넓히지 않는다. 일회성 발견을 기록하기 위해 큰 분석·추상화 작업을 추가하지 않는다.

### 재검토와 승격

관련 기능의 착수·종료 시 필요할 때 해당 후보만 재검토한다. 주기적인 전수 점검이나 자동 실행을 기본으로 만들지 않는다.

- **채택:** 채택 결정과 범위가 확인되면 중복을 확인하고 목표·범위/비범위·AC·검증 방법을 갖춘 독립 Issue를 만든다. 주요 Area 하나와 필요한 작업 성격 Label을 붙이고, 명확한 달성 목표가 있을 때만 Milestone을 지정한다. 출처 이슈와 연결하고 원래 Inbox 댓글에 판단·승격 이슈 링크를 회신한다.
- **기존 이슈에 반영:** 기존 작업의 합의된 범위·AC에 포함할 수 있으면 그 이슈를 보완하고 Inbox 댓글에 연결한다. 단순 관련성으로 blockedBy/blocks를 추가하지 않는다.
- **보류 / 폐기:** 이유와 재검토 조건 또는 폐기 근거를 원래 스레드에 남긴다. 기록을 지우거나 Inbox 전체를 완료 처리하지 않는다.

이 운영 기준의 원문은 이 문서, 후보·처리 판단은 PIN-53 댓글, 채택한 작업의 실행·검증은 독립 Issue가 각각 소유한다. 근거: 2026-10-24 사용자 요청과 PIN-53 운영 원칙, 현행 Area Label 및 포괄 Milestone 설명.

## 이슈와 기록

지정된 이슈의 현재 내용부터 읽는다. 새 이슈가 필요하면 관련 범위의 기존·중복 이슈를 검색한다. 배경·목표·범위/범위 밖·AC·검증 방법·근거 링크를 기록하고 범위 변경 시 제목/본문/AC를 함께 갱신한다.

기존 담당자·프로젝트·마일스톤·주기·우선순위·라벨은 요청/근거 없이 바꾸지 않는다. 없는 상태·라벨·프로젝트를 선제적으로 만들지 않는다. 문서 원문은 저장소 링크로 연결하고 초안 전문/반복 댓글은 최종 요약으로 대체한다.

쓰기 전 현재 값·PR 연결·기존 결과 기록을 조회한다. 이미 반영되면 쓰기를 생략하고 필요한 차이만 갱신한다. 실제 비공개 학습 콘텐츠·사용자 데이터·비밀 값은 본문/댓글/첨부에 복제하지 않는다.

정책·운영 지침을 정하는 이슈는 [문서 정책의 기록 기준](documentation-policy.md#정책-채택과-기록-위치)에 따라 저장소의 원문과 조건별 진입점을 연결한다. 변경별 계획·검증·운영 결과는 해당 변경 이슈가 소유하며 PR은 요약과 링크를 남긴다. DB 스키마 변경은 [API DB 변경 지침의 기록 양식](../apps/api/docs/database-migrations.md#변경별-linear-기록-양식)을 사용한다. 문서 작성만으로 완료하는 이슈에는 실제 DB 검증·배포를 수행했다고 기록하지 않는다.

## 상태와 자동화의 주체

| 항목 | 주체와 기준 |
| --- | --- |
| Backlog / Todo | 미정리 후보 / 범위·AC가 정리된 작업 |
| In Progress | 실제 착수 시 필요한 수동 갱신 |
| 일반 PR 생성 → In Review | 기존 Linear 자동화; Codex는 확인만 |
| PR 병합 → Done | 기존 Linear 자동화; Codex는 확인·결과 보완 |
| PR 없는 작업의 완료 | 실제 AC 충족 후 필요한 수동 갱신 |
| Canceled / Duplicate | 실제 폐기 / 대표 이슈 확인과 연결 |

현재 팀에 Blocked 상태는 없다. 차단 사유·해소 조건을 기록하고 실제 의존이 있을 때 blockedBy/blocks를 사용한다.

자동 Done이 실제 AC 충족을 증명하지는 않는다. PR 하나로 완료되지 않는 배포·DB 적용·상위 과제·다중 PR은 연결 전에 범위 분리와 PR 관계를 정한다. 완결되는 작업에만 closing 연결을 사용하고 부분 기여는 관련 연결로 남긴다. 관련 없음/단순 참고 이슈까지 closing 대상으로 넣지 않는다.

자동 완료 뒤 AC가 남으면 사실과 잔여 작업을 기록하고 범위/연결을 보완한다. 자동화와 경쟁해 상태를 반복해서 되돌리지 않는다.

## 확인한 자동화와 확인 범위

사용자가 제공한 2026-10-02 Pin 팀 Workflows & automations 화면 기준:

| 이벤트 | 규칙 | Codex 동작 |
| --- | --- | --- |
| Draft PR 생성 | No action | In Review로 임의 전환하지 않음 |
| 일반 PR 생성 | In Review | 같은 상태 전환 생략 |
| Review request/activity | No action | 자동화 없는 전환을 선제 추가하지 않음 |
| Ready for merge | No action | 병합 전 Done 처리하지 않음 |
| PR merge | Done | 같은 상태 전환 생략 |

확인 자료: [Pin 팀 설정](https://linear.app/pin-dev/settings/teams/PIN/workflow) 화면과 [PIN-31](https://linear.app/pin-dev/issue/PIN-31). Connector로 팀 상태 목록·프로젝트를 확인했다. 브라우저는 로그인이 필요해 추가 설정을 실시간으로 전수 확인하지 못했다.

화면에 branch-specific 규칙 목록은 보이지 않지만 규칙이 전혀 없다고 단정하지 않는다. 프로젝트별 담당자/라벨/주기/연결 자동화와 추가 대상 브랜치 규칙은 미확인이다. 관련 필드를 변경할 때만 설정을 확인하고 이벤트·조건·필드·관리 주체를 기록한다. 매 작업마다 모든 설정을 다시 읽지 않는다.

## 자동화와 중복하지 않는 종료

PR 제목/본문에 PIN 이슈를 식별할 수 있게 연결한다. 자동으로 연결된 PR·상태는 다시 쓰지 않는다. 이미 있는 검증·결과도 반복 댓글로 추가하지 않는다.

자동화 지연 시 즉시 수동 전환하지 말고 현재 이슈·PR 연결·대상 브랜치·조건을 확인한다. 실제 착수, PR 없는 작업, 확인된 연동 실패만 기존 요청 범위에서 필요한 수동 변경을 하고 사유를 남긴다.

최종 기록은 변경·현재 문서 링크·검증 결과·병합 SHA·남은 제한으로 요약한다. 계획/초안/구현/검증/운영 적용을 구분하고 기존 메타데이터와 자동화 설정을 보존한다. 이 문서는 상태 자동화를 새로 구현하거나 변경하지 않는다.
