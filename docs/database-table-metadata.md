# 신규 테이블 메타데이터 기준

상태: PIN-56에서 채택한 신규 테이블 설계 기준, 2026-10-25. 기존 테이블에 소급해서 컬럼을 추가하지 않는다. API의 DB 변경·검증은 [DB 변경 지침](../apps/api/docs/database-migrations.md)을 따른다.

| 유형 | 필수 또는 조건부 메타 | 예외와 근거 |
| --- | --- | --- |
| 변경 가능한 업무 객체 | 안정된 ID, 생성 시각·주체, 수정 시각·주체, 경합을 검출할 revision | 자동 생성 객체는 사용자 대신 system/operation 출처를 명시한다. revision과 updated_at의 역할을 혼동하지 않는다. 실제 수정 기능을 만들 때 갱신 규칙을 함께 검증한다. |
| 개인 소유 객체 | 인증 사용자에서 결정한 owner와 소유 관련 객체 FK | 관리자 역할을 타인 자료 접근 권한으로 해석하지 않는다. 요청 body의 owner/작성자를 신뢰하지 않는다. 연결 대상도 owner 복합 FK나 동등한 서버 제약으로 제한한다. |
| 불변 원천·적재 결과 | 생성 시각, 생성 주체/owner, 배치·파일·행 계보, 파서 버전·검증 상태 | 수동 보정용 updated_at/updated_by/revision을 두지 않는다. 원천 재처리·정정은 기존 행 덮어쓰기와 구별해 후속 버전/관계로 설계한다. 원파일과 파서 출력은 동일하지 않다. |
| 배치·연결 테이블 | 충돌 없는 단일 또는 복합 PK, 참조 무결성, 필요한 owner | 독립적인 객체 생애주기가 없으면 별도 surrogate ID/created_at/updated_at을 강제하지 않는다. 이벤트 추적이 필요할 때만 연결 시각·주체를 추가한다. |
| 파생 결과 | 사용한 원천·보정 revision/계산 버전과 기준 시각 | 미확인 입력으로 전체 결과를 만들지 않는다. 실시간 계산과 보존 snapshot은 별도 계약이다. |

개별 테이블 설계에는 수정 가능 여부, 삭제 단위·cascade 영향, 재시도 유일성, 생성/수정 주체의 도출 경로를 설명한다. soft-delete는 기본값이 아니다. 개인정보 삭제·보존·백업과 재적재 시 부활 방지 요구가 확인되면 해당 객체의 계약으로 추가한다. 공통 audit helper·범용 이벤트 플랫폼을 먼저 만들지 않는다.

PIN-56 Raw는 배치의 owner가 작성 주체이며 파일·행도 같은 owner에 복합 FK로 묶인다. 모든 행에 created_by를 중복 저장하지 않는다. 파일의 created_at은 최초 반영 시각, 행은 파일의 생애주기를 따른다. 처리 결과가 성공한 파일만 한 트랜잭션으로 저장하며 실패한 파싱 내용은 DB에 남기지 않는다. 파일별 실패/재시도는 UI에서 구별한다. 실제 적용·검증 결과는 [PIN-56](https://linear.app/pin-dev/issue/PIN-56)이 소유한다.
