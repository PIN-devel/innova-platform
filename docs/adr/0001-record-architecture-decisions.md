# ADR-0001: 아키텍처 결정 기록(ADR) 도입 및 운영 체계

- 상태: 승인됨(Accepted)
- 결정일: 2026-11-01
- 적용 범위: 저장소 공통
- 관련 이슈: Linear [PIN-72](https://linear.app/pin-dev/issue/PIN-72)

## 1. 맥락과 문제 정의 (Context)

- 현재 저장소(`innova-platform`)는 React(`apps/web`), Fastify(`apps/api`), 공유 Zod 계약(`packages/contracts`)으로 구성된 pnpm 워크스페이스 모노레포다.
- 프로젝트가 발전함에 따라 데이터 흐름, 패키지 간 경계, 인증/인가 방식, 상태 관리 등 시스템 전반에 중대한 영향을 미치는 아키텍처 결정이 지속적으로 발생한다.
- 기존에는 이러한 설계 논의가 Linear 이슈나 개별 문서(`apps/web/docs/architecture.md` 등)에 기록되었으나, "왜 그렇게 결정했는지(Why)", "어떤 대안을 검토했는지", "어떤 트레이드오프를 수용했는지"를 시계열로 단일하게 추적하기 어려웠다.
- 팀원과 AI 에이전트가 향후 설계를 변경하거나 새로운 기술을 도입할 때 과거 결정의 맥락을 빠르고 신뢰성 있게 참조할 수 있는 체계가 필요하다.

## 2. 검토한 대안 (Considered Options)

### 대안 1: Linear 이슈 및 PR 설명에만 결정 기록
- **개요**: 별도 문서 없이 Linear 작업 티켓과 GitHub PR 본문에 결정 사유를 남기는 방식.
- **장점**: 저장소 내 문서를 추가·유지하는 비용이 들지 않음.
- **단점 및 미채택 사유**:
  - 코드베이스와 분리되어 있어 특정 기술 결정의 맥락을 찾기 위해 외부 이슈를 일일이 검색해야 함.
  - 시간이 흐른 뒤 과거 이슈가 아카이빙되거나 상태가 종결되면 프로젝트 전체 관점에서의 아키텍처 변천사를 조망하기 어려움.

### 대안 2: 개별 앱 디렉터리(`apps/<app>/docs/adr/`)로 분산 관리
- **개요**: 각 앱 단위로 독립된 ADR 디렉터리를 두어 관리하는 방식.
- **장점**: 각 앱의 소유권을 명확히 분리할 수 있음.
- **단점 및 미채택 사유**:
  - 모노레포 특성상 공통 계약(`packages/contracts`), 인프라, 인증 흐름 등 크로스커팅(cross-cutting) 관심사에 대한 결정을 어디에 둘지 모호해짐.
  - ADR 번호 체계가 앱별로 파편화되어 전체 저장소 차원의 탐색 비용이 증가함.

### 대안 3: `docs/adr/` 단일 디렉토리에 시계열 중앙 관리 (채택안)
- **개요**: 저장소 루트의 `docs/adr/` 디렉토리에 `NNNN-short-title.md` 형식으로 모든 아키텍처 결정을 일원화하여 관리하고, 메타데이터의 `적용 범위(Scope)` 필드로 대상 앱을 구분하는 방식.
- **장점**:
  - 코드베이스와 함께 Git으로 버전 관리되어 오프라인에서도 완전한 히스토리 탐색 가능.
  - 단일 번호 체계(`0001`, `0002`...)로 관리되어 결정의 선후 관계가 명확함.
  - 모노레포 공통 영역과 개별 앱 영역을 일관된 표준 템플릿으로 포괄 가능.
- **단점 및 위험 요소**:
  - 경미한 변경까지 무분별하게 ADR로 작성할 경우 관리 오버헤드가 발생할 수 있음 (명확한 작성 기준 설정으로 완화).

## 3. 결정 (Decision)

1. **중앙 집중형 디렉터리 도입**:
   - 모든 아키텍처 결정은 `docs/adr/` 하위에 저장한다.
   - 파일명은 `NNNN-short-kebab-case-title.md` 형식을 사용하며, 4자리 0 패딩 숫자를 부여한다. (예: `0001-record-architecture-decisions.md`)
   - 파일명에는 `draft`, `accepted`, `v2` 등의 상태를 포함하지 않으며, 본문의 `상태` 메타데이터로 구분한다.

2. **표준 템플릿 준수**:
   - 신규 ADR은 `docs/adr/template.md`를 기반으로 작성한다.
   - 필수 메타데이터(상태, 결정일, 작성자, 적용 범위, 관련 이슈)와 핵심 섹션(맥락, 검토한 대안, 결정, 결과와 영향)을 포함한다.

3. **불변성(Immutability) 원칙**:
   - 한 번 승인됨(Accepted) 상태가 된 ADR은 본문 내용을 수정하여 결정을 번복하지 않는다. (오탈자 및 링크 교정만 예외적으로 허용)
   - 결정이 변경되거나 대체될 경우 새 ADR을 작성하고, 기존 ADR의 상태를 `대체됨 (Superseded by ADR-XXXX)`으로 갱신하여 상호 링크한다.

4. **작성 기준(Scope of Decision)**:
   - 되돌리기 어렵거나 비용이 큰 결정(One-way door decision), 새 프레임워크/라이브러리 도입, 패키지 경계 및 인터페이스 설계 원칙, 인증/인가 방식 변경 등에 한해 작성한다.
   - 단순 비즈니스 로직 추가, 버그 수정, 일상적 리팩터링은 ADR 대상이 아니며 Linear 이슈와 PR로 소유한다.

## 4. 결과와 영향 (Consequences)

### 긍정적 영향 (Pros)
- 아키텍처 의사결정의 투명성과 근거가 코드와 함께 영구 보존됨.
- 신규 참여자 및 AI 에이전트가 "현재 시스템이 왜 이렇게 설계되었는가"를 빠르고 정확하게 파악할 수 있음.
- 기술 도입 시 대안 비교와 트레이드오프 검토를 필수화하여 충동적이거나 근거 없는 기술 도입 방지.

### 감수할 비용 및 트레이드오프 (Cons & Trade-offs)
- 중대한 아키텍처 결정 시 ADR 작성 및 문서 검토에 추가 시간 소요.
- 번호 충돌을 방지하기 위해 PR 머지 시점에 번호 중복 여부를 확인할 필요가 있음.

### 후속 작업 / 영향받는 영역
- `docs/documentation-policy.md`의 역할과 위치 테이블에 `docs/adr/` 추가.
- 루트 `README.md`의 문서 진입점 테이블에 ADR 탐색 경로 안내 추가.
